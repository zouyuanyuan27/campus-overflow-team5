## 二、团队价值观

以下条目不是口号，是出现分歧或事故时的裁决依据。

1. **承诺过的事必须交付，做不到提前说。**
   无法完成的任务须在截止时间前 24 小时在群里说明原因并找人接手，不接受到期后才告知做不完。

2. **全员协作项没有"我不知道"。**
   面向全队的协作任务（如 Lab 1 hello 文档、Lab 7 深度评审）由 PO 或 SM 在群里通知全员，每人须回复确认。

3. **对事不对人，提意见必须带方案。**
   "这里不好"不构成评审意见，须写成"这里会重复加分，建议用 `(event_id, user_id, reason)` 唯一键做幂等"这类可执行的改进建议。

4. **互相兜底，但不代做。**
   主动帮助卡住的队友、共享排查思路；但不替别人写代码、不把别人的任务整个扛过来。讲清楚比动手代劳更负责任。

5. **学术诚信是硬红线。**
   不以删除测试、放宽断言、篡改覆盖率门禁的方式让 CI 变绿；认为既有测试与需求矛盾时，在 PR 中说明并与教师确认。

6. **文档与代码同等重要。**
   改了行为而没改文档，视为未完工。ADR、错误码表、README 随代码一起更新。

7. **允许说不熟练。**
   队里多数人是第一次做团队项目。不会就问，闷头三天最后交个错的才丢人。

## 三、沟通约定

### 3.1 渠道与响应时限

| 渠道                   | 用途                  | 响应要求          |
| -------------------- | ------------------- | ------------- |
| 团队 QQ群               | 日常异步沟通、PR 通知、进度同步   | 工作日 4 小时内回复确认 |
| GitHub PR / Issue 评论 | 技术讨论、代码评审           | 24 小时内        |
| 电话 / 语音              | 距截止时间不足 4 小时的阻塞     | 立即接通          |
| 线下（课间、实验课）           | 需求澄清、故事地图、Sprint 规划 | 当场            |

这里的"响应"指确认收到并给出下一步时间点，不是要求在该时限内解决问题。

### 3.2 @ 规则

- `@具体人`：要求此人采取行动，被 @ 的人必须回复。
- `@所有人`：仅限全员协作项提醒与截止时间当天提醒，每天最多两次。
- 技术提问不 @ 所有人，先 @ 一位相关同学，解决不了再升级给 SM。

### 3.3 会议节奏

| 会议         | 时间             | 时长    | 主持      |
| ---------- | -------------- | ----- | ------- |
| 周站会        | 每周固定时间（群内约定）   | 15 分钟 | 李增艳（SM） |
| Sprint 规划会 | 每个 Sprint 第一天  | 60 分钟 | 邹园园（PO） |
| Sprint 评审会 | 每个 Sprint 最后一天 | 30 分钟 | 邹园园（PO） |
| Sprint 回顾会 | 评审会后           | 20 分钟 | 李增艳（SM） |

站会三句话：昨天做了什么、今天要做什么、有什么阻塞。站着开，超时话题会后单独沟通。

### 3.4 看板

- 看板列：To Do / In Progress / In Review / Done。
- 卡片状态由责任人本人更新，SM 负责整体维护，任务状态变动在 24 小时内反映到看板。
- 卡片卡在同一列超过两天，责任人在站会上说明原因，无法自行解决的由 SM 协调清除阻塞。

### 3.5 决策机制

- 技术分歧讨论不超过 15 分钟仍无结论的，由 PO 拍板，全队执行，不再反复。
- 涉及架构约束的，先查 `docs/adr/`；仍冲突的记录下来向教师确认。
- SM 不替代 PO 决定产品方向，不替代 Developer 决定技术方案；需求优先级只有 PO 可以调整。

### 3.6 缺席与产能变动

- 不能参会须提前在群里说明，指定交接人，并把进度写进看板卡片。
- 缺席超过一周，由 SM 重新分配其未完成任务并在群里公示。
- 个人产能下降时，主动告知 SM，共同调整 Backlog，不硬撑到截止日才暴露。

## 四、开发规约

### 4.1 分支与提交

- 分支命名 `feature/<姓名拼音>-<主题>`，从 `main` 切出，存活不超过 3 天。
- 提交信息格式 `<type>(<scope>): <中文说明>`，一个 commit 只做一件事。
- `main` 分支受保护，禁止直接 push，所有改动经 Pull Request 合入。

### 4.2 代码与架构

| 约束    | 具体要求                                                | 依据                           |
| ----- | --------------------------------------------------- | ---------------------------- |
| 架构边界  | 领域层零框架依赖；跨限界上下文只经 `*-api`；依赖无环；表名加上下文前缀             | `ArchitectureTest`（ArchUnit） |
| 既有代码  | `*-api`、基础设施适配器、安全链路、Flyway 迁移不重写                   | README 第 2 节                 |
| 错误码   | 领域异常遵循 `docs/错误码.md` 的分段规则与 HTTP 映射                 | 课程材料                         |
| 事务与事件 | 领域事件先落 `outbox_event` 再投递，消费端必须幂等                   | ADR 002、README 第 8 节         |
| 测试断言  | 禁止修改既有测试的断言；有疑问在 PR 中说明                             | README 第 3 节                 |
| 覆盖率   | 领域层不低于 70%，Lab 7 调高 `domain.coverage.minimum` 后仍须通过 | README 第 5 节                 |

### 4.3 语言与格式

- 后端：JDK 21，沿用仓库现有代码风格，提交前做格式化，但不整文件重排以免淹没 diff。
- 前端：TypeScript，提交前 `npm run typecheck` 必须通过。
- 注释与文档使用中文，代码标识符使用英文。
- 文件名只用英文或拼音，不使用中文文件名。

### 4.4 测试与代码评审

- 交付的业务代码必须带对应的单元测试，重点覆盖领域层业务规则。
- 每人每个 Sprint 至少完成 2 次实质性 PR 评审；Lab 7 阶段按 Step 4 要求，每人选择 1 个自己未参与的 PR 做深度评审，留下不少于 5 条实质性意见。
- 评审按六个维度展开：正确性、可读性、可测性、安全、性能、风格。
- 评审意见区分 `must` 与 `suggest`：`must` 项未解决不允许合并，`suggest` 项作者须回复说明采纳与否。

### 4.5 安全与隐私

- 仓库为公开仓库，不提交学号、手机号、真实邮箱等个人信息，学号仅登记在纸质承诺书上。
- 不提交密钥、数据库口令、`.env` 文件；本地配置走环境变量或已被忽略的本地配置文件。

### 4.6 工作量承诺

- 每人每个 Sprint 至少承担 3 个 Story Point 的工作量。
- 承诺的工作量以 Sprint 规划会估算为准，实际产能变化时由 PO 与 SM 调整 Backlog，个人不擅自削减承诺范围。

### 4.7 提交前自检

- [ ] 本地跑通过相关模块测试
- [ ] 未改动既有测试的断言
- [ ] 未混入本地配置、密钥、个人信息
- [ ] 文档（README、ADR、错误码表）已同步更新
- [ ] 提交信息能让人一眼看懂做了什么

## 五、完成的定义（Definition of Done）

### 5.1 Pull Request 级

- [ ] CI（GitHub Actions）全绿
- [ ] 至少 1 名非作者给出 LGTM
- [ ] 所有 `must` 级评审意见已解决，其余意见已回复
- [ ] 涉及业务代码的改动已附带测试
- [ ] 分支命名与提交信息符合 4.1

### 5.2 用户故事级

- [ ] 该故事的全部 Gherkin 验收场景（不少于 3 个：快乐路径、边界路径、异常路径）已编写并通过
- [ ] 代码已合入 `main`，CI 全绿
- [ ] 核心业务规则有领域层测试覆盖
- [ ] 涉及的架构约束（ArchUnit）校验通过
- [ ] 相关文档已更新
- [ ] PO 在演示环境实际操作确认，而非仅阅读代码

### 5.3 Sprint 级

- [ ] Sprint 目标达成，承诺的故事全部通过故事级 DoD；未完成的说明原因并移回 Backlog
- [ ] `mvn verify` 端到端集成测试通过
- [ ] 领域层覆盖率达标，ArchUnit 全绿
- [ ] 前端 `npm run typecheck` 与 `npm run build` 通过
- [ ] 看板已更新，回顾会已召开，改进项已进 Backlog

任一条不满足，该事项即不能计入本 Sprint 完成量。
